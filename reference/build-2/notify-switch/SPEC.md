# homebridge-notify-switch Specification

Status: Current as of 1.3.2
Repository: https://github.com/arodbuilds/homebridge-notify-switch
Package: homebridge-notify-switch
Author: arodbuilds

## 1. Purpose

A Homebridge dynamic platform plugin that exposes HomeKit switches. Each switch is always off. Turning it on sends one or more preset messages through configured providers and the switch returns to off on its own. Switches are meant to be triggered by HomeKit automations and scenes, giving any HomeKit event a way to notify people by SMS, email, Telegram, or ntfy push notification.

## 2. Goals and non-goals

### Goals

1. One plugin, multiple channels, one configuration model.
2. Minimum viable setup is a single provider, a single group, a single switch, configurable entirely from the Homebridge UI with no config.json editing.
3. Meets every current Homebridge Verified requirement.
4. Runs comfortably on a Raspberry Pi Zero.
5. Credentials are handled with least privilege and never logged.
6. Configuration shape supports future channels without migration.

### Non-goals

1. Inbound messages or replies.
2. Delivery status callbacks or webhooks.
3. MMS or attachments.
4. WhatsApp (on the roadmap below, not in the current release).
5. Fallback routing (send on channel B only if channel A fails). Every configured channel is sent in parallel.

### Roadmap

Planned, in no particular order and with no dates; each arrives in its own minor release once its design is settled:

1. iMessage for Homebridge hosts running on a Mac, sent through the Messages app on that Mac (1.4.0).
2. Twilio voice: a call that reads the message aloud.
3. WhatsApp through Twilio, using one approved utility template with the message body as its variable, so no per-message template approval is needed.
4. Telnyx SMS as a second SMS provider.
5. Discord and Slack incoming webhooks as channels.
6. Matter exposure of the switches once Homebridge's Matter support is stable.

## 3. Terminology

1. Provider: a configured connection to an external messaging service. Types: `twilio`, `smtp`, `telegram`, and, from 1.1.0, `ntfy`.
2. Channel: the kind of message a provider can send. Channels: `sms`, `email`, `telegram`, `ntfy`. The Twilio provider can serve both `sms` and `email`; the ntfy provider serves `ntfy`.
3. Recipient group: a named list of people, holding an address list per channel.
4. Switch: a HomeKit switch accessory with one or more actions.
5. Action: one send on one provider, with its own message body, targeting one or more groups and optionally extra individual recipients. Actions are the stored form in config.json; from 1.1.0 the custom UI does not show them and derives them from the switch editor (section 11.2, item 8).
6. Platform default: the provider switches use on a channel when more than one provider serves it and the action does not name one (section 5.7).

## 4. Platform and accessory model

1. Plugin type: dynamic platform. `pluginAlias` is `NotifySwitch`. `singular` is true (one platform block).
2. Each configured switch becomes one accessory with a `Switch` service.
3. Each switch has a stable `id` (UUID v4 generated by the UI when created; also accepted if typed). The accessory UUID is derived from `id`, never from the display name, so renames do not orphan the accessory in HomeKit.
4. On startup the platform registers accessories for every valid switch and unregisters any cached accessory whose `id` is no longer in config.
5. Optional per switch: a `ContactSensor` service that trips on send failure (see section 9). Default off.
6. Optional platform-level master switch named by the user (default "Notifications Enabled"). When off, no switch sends anything; flips are logged as suppressed. Default enabled and shown.
7. The plugin does not register any accessory if the platform config is missing or fails validation. It logs the reasons and exits its startup path cleanly. It never throws. Cached accessories are left untouched in that case, so HomeKit automations survive a typo.
8. Child bridge is supported and recommended in the README.
9. A configuration that passes validation with zero switches (a fresh install, or after Reset plugin to fresh install in the settings UI) registers nothing and unregisters every cached accessory, the master switch included. The state persisted in their contexts (the master switch position and the failure sensor state) is cleared with them.

### 5.1 Platform fields

1. `name` (string, required). Platform display name. Homebridge prefixes every log line with it, so it follows the display name rule of section 5.2 (a startup warning, never an error).
2. `configVersion` (integer, hidden, default 1). Used for future migrations.
3. `defaultCountry` (ISO 3166-1 alpha-2, default `US`). Used by the UI phone number entry and by startup normalization of numbers lacking a plus sign. The custom UI prefills it on first load from the browser locale, else from the Homebridge host's time zone, else `US` (section 11.2, item 21); startup normalization always uses the saved value, `US` when absent.
4. `masterSwitch.enabled` (boolean, default true). Whether to expose the master switch accessory.
5. `masterSwitch.name` (string, default "Notifications Enabled").
6. `debug` (boolean, default false). Verbose logging; never includes secrets even when on.
7. `defaultProviders` (object, optional, from 1.1.0). Maps a channel (`sms`, `email`, `telegram`, `ntfy`) to the id of the provider switches use on that channel unless an action names another. Only channels with more than one provider carry an entry (section 5.7).
8. `timeFormat` (enum `12h`, `24h`; default `12h`, from 1.2.0). How `{{time}}` and the time part of `{{datetime}}` render (section 5.6).
9. `dateFormat` (enum `mdy`, `dmy`, `ymd`; default `mdy`, from 1.2.0). How `{{date}}` and the date part of `{{datetime}}` render (section 5.6).

Both are closed enums. A missing field means the default. An invalid value is handled exactly as an invalid `defaultCountry`: a startup error at `platform.timeFormat` or `platform.dateFormat` (`must be one of 12h, 24h`), with the default used for the rest of the validation pass. The custom UI shows both under Settings, directly below Default Country (section 11.2, item 27), and writes them with the next Save like Default Country; a stored value it does not recognise is shown and written as the default. Reset plugin to fresh install keeps the defaults. The schema form carries both as enums with the same titles (`Time format`, `Date format`) and one-line descriptions.

### 5.2 Provider fields

Common to all providers: `id` (slug, unique, required), `type` (enum, required), `name` (display name, required).

Display name rule (providers and groups, from 1.1.0): printable characters only, no control characters (C0, C1, DEL, the line and paragraph separators), no angle brackets, 1 to 64 characters; pattern `^[^\u0000-\u001F\u007F-\u009F\u2028\u2029<>]{1,64}$`, in the spirit of the switch name rule. `config.schema.json` and the custom UI enforce it (validation message in section 11.3: "Use letters, numbers, spaces, and punctuation, up to 64 characters."); startup validation reports a name that breaks it as a warning naming the field (`providers[0].name`, `groups[0].name`, `platform.name`), never an error, so an existing configuration keeps starting.

Twilio (`type: twilio`). Serves channels `sms` and `email`.

1. `accountSid` (required, pattern `^AC[0-9a-fA-F]{32}$`).
2. `apiKeySid` (required, pattern `^SK[0-9a-fA-F]{32}$`).
3. `apiKeySecret` (required, password field).
4. `smsSenders` (array of E.164 strings, `uniqueItems`). At least one of `smsSenders` or `messagingServiceSid` is required to use the `sms` channel.
5. `messagingServiceSid` (optional, pattern `^MG[0-9a-fA-F]{32}$`). When present it must match; an empty string is rejected by the schema, so the custom UI omits the key when the field is blank.
6. `emailFrom.address` and `emailFrom.name` (optional). Required to use the `email` channel. The address domain must be authenticated in the Twilio Console under Communications > Email > Domains. The field stays optional in the schema; an email action on a Twilio provider without `emailFrom.address` is a startup validation error (`switches[i].actions[j].channel: provider "x" cannot send email until emailFrom.address is set on it`), which the custom UI shows on the switch's Email provider dropdown rather than prompting for the address (a Twilio provider without it does not count as an email provider for the platform defaults of section 5.7).

Auth Token is deliberately not accepted. The README and field help explain that an API key can be revoked without rotating the account's master credential.

SMTP (`type: smtp`). Serves channel `email`.

1. `host` (required).
2. `port` (integer, required, default 465).
3. `security` (enum `ssl`, `starttls`, `none`; default `ssl`). Maps to nodemailer `secure: true`, `requireTLS: true`, and neither, respectively. With `none` nodemailer still upgrades opportunistically with STARTTLS when the server offers it, with certificate verification on.
4. `username` (required).
5. `password` (required, password field).
6. `from.address` (required, email format) and `from.name` (optional).
7. `smtpPreset` (optional, string). The mail provider preset the custom UI last chose (`fastmail`, `gmail`, `icloud`, `outlook`, `yahoo`, `zoho`), kept for redisplay only (section 11.2, item 22). The runtime never reads it; `host`, `port` and `security` are the settings that count. `config.schema.json` declares it as an optional string with that enum, hidden from the schema form (which has no picker), so a stored value passes the schema.

No option to disable certificate verification is offered.

Telegram (`type: telegram`). Serves channel `telegram`.

1. `botToken` (required, password field, pattern `^\d+:[A-Za-z0-9_-]{30,}$`).
2. `parseMode` (enum `none`, `markdown`, `html`; default `none`). `markdown` sends the Bot API's legacy `Markdown` mode rather than `MarkdownV2`, which requires escaping most punctuation and would make plain alert text fail with 400; `html` sends `HTML`; `none` omits `parse_mode`.

ntfy (`type: ntfy`, from 1.1.0). Serves channel `ntfy`.

1. `server` (URL, default `https://ntfy.sh`). Must be `http` or `https`, without credentials, query or fragment; a path is allowed for a server behind a prefix; trailing slashes are dropped. The URL parser's normalized form is what the plugin uses and logs.
2. `auth` (enum `none`, `token`, `basic`; default `none`).
3. `token` (password field, required when `auth` is `token`; no whitespace or control characters, up to 256 characters). Sent as `Authorization: Bearer {token}`.
4. `username` and `password` (required when `auth` is `basic`; the username holds no colon). Sent as `Authorization: Basic base64(username:password)`.
5. With `auth` `none`, a `token`, `username` or `password` that is present is ignored with a warning.
6. Optional `credentialsFile` as for the other providers (section 12, item 2): its keys may be `token`, `username` and `password`.

### 5.3 Group fields

1. `id` (slug, unique, required).
2. `name` (display name, required).
3. `sms` (array of E.164 strings, optional, `uniqueItems`).
4. `email` (array of email addresses, optional, `uniqueItems`).
5. `telegram` (array of chat IDs matching `^-?\d+$`, optional, `uniqueItems`).
6. `ntfy` (array of topic names matching `^[A-Za-z0-9_-]{1,64}$`, optional, `uniqueItems`). A topic name is what lets anyone read (and publish to) the topic, so it is masked in info logs like a chat id (`ho***ts`).

A group with no addresses is valid but produces a startup warning if any switch references it. Each of the four lists holds at most 200 entries (section 12, item 12). The display name rule of section 5.2 applies to `name`.

### 5.4 Switch fields

1. `id` (UUID, required, generated by the UI).
2. `name` (required). Must satisfy HAP naming: pattern `^[A-Za-z0-9][A-Za-z0-9 ']*[A-Za-z0-9]$`, max 64 characters. Unique across switches.
3. `enabled` (boolean, default true). Disabled switches are still registered but do nothing when flipped, and log the suppression.
4. `cooldownSeconds` (integer, 0 to 86400, default 0). Flips within the cooldown window are logged and ignored.
5. `failureMode` (enum `any`, `all`, `off`; default `any`). Governs when the failure sensor trips and how the result is logged. `any`: any recipient on any channel failing counts as failure. `all`: only when every recipient on every channel fails. `off`: never trips the sensor; failures are still logged.
6. `failureSensor` (boolean, default false). Adds a Contact Sensor service to this accessory. Contact opens on failure and closes on the next successful send or after `failureSensorResetSeconds`.
7. `failureSensorResetSeconds` (integer, default 300). 0 keeps the sensor open until the next successful send.
8. `actions` (array, `minItems` 1). Actions remain the stored form of what a switch sends. From 1.1.0 the custom UI does not edit them directly: it shows the switch editor of section 11.2, item 8 (recipients, channels, one message) and derives the array from it, one action per enabled channel, and reads a stored array back into that form losslessly. A stored switch with more than one action on the same channel cannot be read into that form; the custom UI shows such a configuration not at all (section 11.2, item 26), while startup runs it as before. The schema form and hand edits keep writing actions as before.

### 5.5 Action fields

1. `providerId` (required). Must reference an existing provider.
2. `channel` (enum `sms`, `email`, `telegram`, `ntfy`, required). Must be a channel the referenced provider serves.
3. `sender` (optional, sms only; when present it must be E.164, an empty string is rejected by the schema and the custom UI omits a blank sender). One of the provider's `smsSenders`. If omitted and the provider has exactly one sender, that sender is used (also when `messagingServiceSid` is set: the rules apply in this order). If omitted otherwise and `messagingServiceSid` is set, the Messaging Service is used.
4. `groups` (array of group ids, optional).
5. `recipients` (array of addresses for this channel, optional).
6. At least one of `groups` or `recipients` must resolve to one or more addresses, and at most 100 after deduplication (section 12, item 12).
7. `subject` (email and ntfy, optional, default is the switch name). The email subject, or the ntfy notification title. CR and LF are stripped; the ntfy provider strips every control character from the title and RFC 2047 encodes it when it holds anything outside printable ASCII. Set on another channel it is ignored with a startup warning.
8. `body` (required). Constraints by channel:
   sms: 1 to 160 characters, GSM-7 character set enforced by validation at startup and by the custom UI. `config.schema.json` cannot carry the pattern because `body` is one field shared by every channel, so the schema form's description combines the sms and email/telegram help. The custom UI shows a live character and segment counter.
   email: 1 to 10000 characters. Sent as plain text; HTML is not supported in v1.
   telegram: 1 to 4096 characters. Sent with the provider's `parseMode`.
   ntfy: 1 to 4096 characters, plain text. ntfy.sh limits a message to 4096 bytes, so a body near the limit with many non-ASCII characters is refused by the server with 413.
9. `bcc` (email only, boolean, default false). "Hide recipients from each other (BCC)": when true and the action resolves to more than one recipient, the recipients go in Bcc and the from address in To (sections 6.2 and 6.3). A message to a single recipient always uses To. Set on another channel it is ignored with a startup warning.
10. `priority` (ntfy only, enum `min`, `low`, `default`, `high`, `urgent`; default `default`). Sent as the `Priority` header in its word form. Set on another channel it is ignored with a startup warning.
11. `tags` (ntfy only, array of strings each matching `^[A-Za-z0-9_+-]{1,32}$`, at most 8, duplicates dropped). Sent comma-joined in the `Tags` header; omitted when empty. Set on another channel it is ignored with a startup warning.
12. A switch holds at most 20 actions (section 12, item 12).

### 5.6 Template variables

Available in `body` and `subject` (the email subject or the ntfy title): `{{switchName}}`, `{{time}}`, `{{date}}` and `{{datetime}}`. Unknown variables are left as typed. The time zone is the Homebridge host's; the formats follow the platform's `timeFormat` and `dateFormat` (section 5.1), rendered by `buildTemplateVariables` in `src/template.ts`, which takes the two settings:

1. `{{time}}`: with `12h`, the hour without a leading zero, a colon, two-digit minutes, one space and uppercase AM or PM ("5:15 PM"; midnight is "12:00 AM", noon is "12:00 PM"). With `24h`, two-digit hour and minutes ("17:15"). Never seconds.
2. `{{date}}`: with `mdy`, "9/8/2026"; with `dmy`, "8/9/2026"; with `ymd`, "2026-09-08". Only `ymd` zero-pads the month and day.
3. `{{datetime}}`: the date, one space, the time, in the chosen formats ("9/8/2026 5:15 PM"). No seconds and no zone.

Before 1.2.0 the three rendered as `HH:mm`, `YYYY-MM-DD` and `YYYY-MM-DDTHH:mm:ss`; the old time and date forms are what `24h` and `ymd` give, and `{{datetime}}` no longer carries seconds under any setting.

### 5.7 Platform defaults

From 1.1.0 the platform block carries `defaultProviders`, an object mapping a channel to a provider id. It answers one question: which provider does a switch use on a channel when its action does not say? The runtime never reads it (every stored action carries its `providerId`); the custom UI derives `providerId` from it, and startup validation checks it. The rules, shared by startup validation and the UI (`src/defaults.ts`):

1. A provider serves the channels of its type (section 3, item 2). A Twilio provider serves `email` only once `emailFrom.address` is set.
2. When exactly one provider serves a channel, it is the default. Nothing is shown for it in the UI and nothing is stored; an entry that names it is accepted and ignored.
3. When more than one provider serves a channel, `defaultProviders[channel]` names the default. The UI stores an entry only for such channels and only when it names one of them.
4. A missing entry for a channel with more than one provider falls back to the first of them in configuration order. Startup logs a warning naming the fallback (`platform.defaultProviders.email: 2 providers can send email and none is the default; switches that do not name one use "twilio-main", the first in config order. Choose a default under Settings`). From 1.2.0 this rule is reached only by hand-edited configurations: the custom UI writes the entry the moment it applies (section 11.2, item 25), so a configuration it saved always carries one, and it shows no warning for a missing entry.
5. An entry naming an id that does not exist, a provider whose type does not serve the channel, a Twilio provider without `emailFrom.address` for `email`, a key that is not a channel, or a value that is not a string, is a startup error at `platform.defaultProviders.{channel}` (section 10). The UI replaces such an entry with the current fallback the next time it validates the block, and asks again.
6. Removing the default provider in the UI: if one provider remains for the channel it becomes the default and nothing is stored; if more remain, the UI writes the new fallback (the first remaining validated provider in configuration order) immediately and shows the prompt on the last remaining validated card. Renaming a provider's id under Advanced carries an entry that named it along.
7. In the switch editor a channel's provider is the override the switch stores under Advanced, else the platform default. A stored action whose `providerId` is the channel's resolved default loads as no override, so changing the default later moves that switch with it; one whose `providerId` differs loads as an override and stays put. One whose channel no provider serves any more (the provider it names was removed, or the only provider of its type stopped serving the channel) is kept: it loads with its `providerId` as the override, its channel is listed under Send by disabled with the note "No provider configured for {channel}; add one or untick to remove." (section 11.2, item 8), and it is written back exactly as stored. It is dropped only when the user unticks the channel; adding a provider for the channel makes it an ordinary action again.

## 6. Provider interface

```ts
interface SendRequest {
  channel: Channel;
  sender?: string;
  recipients: string[];
  subject?: string;   // email subject or ntfy title
  body: string;
  bcc?: boolean;      // email only
  priority?: NtfyPriority; // ntfy only
  tags?: string[];    // ntfy only
}

interface RecipientResult {
  recipient: string;
  ok: boolean;
  id?: string;        // provider message id, operation id, etc.
  error?: string;     // sanitized, no secrets, no request dumps
}

interface Provider {
  readonly id: string;
  readonly type: ProviderType;
  readonly channels: Channel[];
  validateConfig(): ValidationIssue[];
  validateBody(channel: Channel, body: string): ValidationIssue[];
  send(req: SendRequest): Promise<RecipientResult[]>;
}
```

Rules:

1. The switch code imports only this interface. Provider modules are loaded lazily by type so an unused provider costs nothing.
2. Every provider request has a 10 second timeout and at most one retry with a 2 second backoff, except when the provider returns a rate limit response with a retry-after value, in which case that value is honored once. SMTP has no retry-after: temporary replies (421, 450, 451, 452) and connection errors are retried once after the standard backoff.
3. Per-provider in-flight concurrency is capped at 5. A provider's HTTP response body is read up to 1 MiB; the rest is discarded and the stream cancelled (section 12, item 12).
4. Providers never throw. All errors resolve to `RecipientResult` entries. One recipient's failure never stops the others: a provider that sends one request per recipient collects the outcomes with `allSettled` semantics (never `Promise.all`), so a 4xx, a thrown error, or a timeout for one recipient changes that recipient's entry only, and every other recipient is still sent and reported.
5. The diagnostics the settings UI server uses (Test connection, Find people and groups, Look up numbers) live on a separate `ProviderDiagnostics` interface; the `Provider` interface above is all the switch code depends on. The render-and-send step is shared between the switch accessory and the settings UI's Test send (`src/send.ts`).

### 6.1 Twilio SMS

POST `https://api.twilio.com/2010-04-01/Accounts/{accountSid}/Messages.json` with Basic auth `apiKeySid:apiKeySecret`, form body `To`, `Body`, and either `From` or `MessagingServiceSid`. One request per recipient, concurrency 5. Success is HTTP 201; the `sid` is returned as `id`. Twilio error `code` and `message` are logged.

### 6.2 Twilio Email

POST `https://comms.twilio.com/v1/Emails` with the same Basic auth, JSON body with `from`, `to` (all recipients in one request, so they see each other), and `content.subject`, `content.text` and `content.html`. The API requires `html`, so the plain body is sent both ways: `text` is the rendered body and `html` is the same body HTML-escaped inside a `pre` element so line breaks survive; no HTML authoring is exposed. With the action's `bcc` option and more than one recipient, the recipients go in `bcc` (the same `{ address }` objects as `to`) and the from address in `to`; a single recipient is always in `to`. Success is HTTP 202; `operationId` is returned as `id` for every recipient. One request per action regardless of recipient count.

From 1.1.1 `content.headers` carries `Auto-Submitted: auto-generated` (RFC 3834, the value for automated messages that are not replies). The endpoint nests custom headers inside `content`, and `Auto-Submitted` is not on its list of headers that may not be overridden. It is the only custom header the plugin sends. Twilio Email adds an open-tracking pixel to every message, and as of September 2026 there is no setting to turn it off, per message or per account: the endpoint documents no tracking field (the SendGrid v3 `tracking_settings` field is not part of it) and the Email settings in the Twilio Console (https://www.twilio.com/docs/email/settings) cover only event forwarding, IP addresses, and the address allow list. So the plugin sends no tracking field and makes no claim about tracking. Twilio Email also sends from shared SendGrid IP addresses whose reputation the household does not control. The README states both and points a household that wants neither at an SMTP provider (section 15, item 3).

### 6.3 SMTP

nodemailer transport built from provider config. One message per action with all recipients in `to` by default. With the action's `bcc` option and more than one recipient, the recipients go in `bcc` and the `from` address in `to` (so the envelope is valid and recipients do not see each other); a single recipient is always in `to`. Success is a resolved `sendMail`; the `messageId` is returned as `id`. Rejected addresses reported by the server are mapped to per-recipient failures (a fully rejected envelope keeps the per-recipient errors). The login is scrubbed from every error string. nodemailer `debug` and `logger` options are never enabled and no `tls` override is passed. From 1.1.1 every message carries the header `Auto-Submitted: auto-generated` (RFC 3834) through nodemailer's `headers` option; it is the only header the plugin adds.

### 6.4 Telegram

POST `https://api.telegram.org/bot{token}/sendMessage` with JSON `chat_id`, `text`, and `parse_mode` when not `none`. One request per chat ID, concurrency 5. Success is `ok: true`; `result.message_id` is returned as `id`. 403 (bot blocked) and 400 (bad chat id) are mapped to readable errors. 429 honors `parameters.retry_after`. The bot token is part of the URL, so it is redacted from every error string.

### 6.5 ntfy

POST `{server}/{topic}` with the rendered body as plain text (`Content-Type: text/plain; charset=utf-8`) and the headers `Title` (the action's `subject`, else the switch name; control characters removed, cut to 200 characters, RFC 2047 encoded outside printable ASCII, omitted when empty), `Priority` (the word form: `min`, `low`, `default`, `high`, `urgent`), `Tags` (comma-joined, only when there are tags) and `Authorization` (`Bearer {token}` or `Basic base64(username:password)`, only when `auth` is not `none`). One request per topic, concurrency 5, the shared 10 s timeout and single retry; 429 honors the `Retry-After` header. Success is HTTP 200 with a JSON body carrying an `id`, returned as `id` per topic; a 200 without one is a failure ("ntfy answered HTTP 200 without a message id; check that the server URL points at an ntfy server"), because a web page at a wrong URL is not a delivery. 401 and 403 map to "ntfy rejected the credentials for topic {topic} (HTTP {status})", 404 to "ntfy server not found (HTTP 404); check the server URL", 413 to "ntfy error 413: the message is too large for this server", 429 to "ntfy error 429: rate limited"; other responses are reduced to ntfy's `code` and `error` fields. The token, the password and the encoded Authorization value are redacted from every error string and never logged.

Test connection (section 11.2, item 3): GET `{server}/v1/health` without credentials; the answer must be HTTP 200 with `healthy: true` (404 reads "ntfy server not found at {server} (HTTP 404). Check the server URL.", anything else "{server} did not answer like an ntfy server (HTTP {status})." or "reports that it is not healthy"). With `auth` set, then GET `{server}/v1/account` with the Authorization header: 200 is "Connected to {server} and the credentials were accepted.", 401 or 403 "ntfy rejected the credentials (HTTP {status}). Check the access token." (or "the username and password"). With `auth` `none` the success line is "Connected to {server}. No credentials are set, so the topics must allow anonymous publishing." Neither request publishes anything; Test send publishes for real.

## 7. Runtime behavior on flip

1. HomeKit sets `On` to true. The handler returns immediately.
2. If the master switch is off, or the switch is disabled, or the cooldown is active, log at info and go to step 8.
3. Resolve recipients for each action: union of referenced groups' lists for that channel plus `recipients`, deduplicated.
4. Render template variables.
5. Fire all actions in parallel. Each provider applies its own concurrency cap.
6. Collect results. Log one line per recipient (see section 8) and one summary line per switch.
7. Evaluate `failureMode` and update the failure sensor if enabled.
8. After 1 second, set `On` back to false and notify HomeKit.

Setting `On` to false from HomeKit is a no-op.

## 8. Logging

1. Info on each send: `[Water Leak Alert] sms via twilio-main to +1678***0101: sent (SM...)`. Phone numbers, email addresses, chat ids and topic names are partially masked in info logs; full addresses appear only when `debug` is true.
2. Warn on each failure with the provider's error code and a short message.
3. Error only for configuration problems at startup.
4. Message bodies are never logged at info. With `debug` true, bodies are logged.
5. Secrets are never logged at any level. Error objects from providers are reduced to code and message before logging.
6. Every line written through the plugin's logger has its control characters escaped (`\n`, `\r`, `\t`, `\u001b`), and every configuration value quoted in a validation message is escaped and cut to 80 characters, so nothing from config.json or a provider's reply can start a new log line or emit a terminal escape sequence (section 12, item 12). With `debug` on, a multi-line body is logged on one line with `\n` in it.

## 9. Failure sensor

1. Service type `ContactSensor`, `ContactSensorState` open (1) means a failure occurred.
2. Trips according to `failureMode`.
3. Resets to closed on the next fully successful send from that switch, or after `failureSensorResetSeconds`.
4. Exposed on the same accessory as the switch so it shares the room and name.

## 10. Startup validation

Validation runs in code, independent of the schema, and reports every issue in one pass with the field path, for example `switches[2].actions[0].providerId: no provider with id "twillio-main" (did you mean "twilio-main"?)`.

Blocking issues (the platform registers nothing and cached accessories stay): invalid provider credentials format, invalid or duplicate ids, a key named `__proto__`, `constructor` or `prototype` anywhere in the block, a bound of section 12, item 12 exceeded, a switch with no resolvable recipients, a body that violates channel constraints, a provider type that does not serve the requested channel, a switch name that violates HAP naming, an action that references a provider or group that does not exist, and a `defaultProviders` entry that names a provider that does not exist or cannot serve its channel, or a key that is not a channel (section 5.7).

An empty or absent `providers` or `switches` list is not an error, and `config.schema.json` requires neither (only `name`), so the schema form and the runtime agree. A switch with more than one action on the same channel is valid and runs every action, as before 1.1.0; only the custom UI declines to edit it (section 11.2, item 26). No switches means nothing is registered and every cached accessory is removed (section 4, item 9); it is logged as a warning.

Warnings (the platform starts): no providers, no switches, a group with no addresses, a provider that no switch uses, a provider, group or platform name that breaks the display name rule (section 5.2, reported at `providers[i].name`, `groups[i].name` or `platform.name`), a sender not in the provider's list when only one sender exists (it is used anyway), a channel with more than one provider and no `defaultProviders` entry (section 5.7, item 4; the first provider in configuration order is named as the fallback), and a switch that targets a group holding addresses on a channel none of its actions send on (an uncovered channel; logged once per switch and channel with the switch name, the group ids and the channel, because those people receive nothing). From 1.1.0 the custom UI no longer shows the uncovered channel as a warning: its Send by checkboxes make the choice explicit (section 11.2, item 8), so the startup warning is for hand-edited configurations and for channels a user unticked.

Phone numbers without a leading plus sign are normalized using `defaultCountry`; the normalized value is logged once at startup so the user can correct config.json if desired.

They supply values the host does not provide inside the iframe: the host posts its body classes (`config-ui-x-{theme}`, `modal-content`, `dark-mode`), its stylesheets and its inline styles into the iframe and never sets `data-bs-theme`, so Bootstrap's own dark values are never in effect there (checked against homebridge-config-ui-x 5.29.0). Text buttons keep their intent colours under the host's dark marker through one override rule for `.btn-link` inside the page; the default-provider prompt and every alert box are left-aligned; the variable tokens in the Variables list are in the link colour.
   Saved status: the handoff shows a status box "Saved. Restart Homebridge to apply." after a successful Save. The page does not show it, because the host gives it no way to know that a Save happened: in `@homebridge/plugin-ui-utils` 2.2.6 the client (`IHomebridgePluginUi`) reacts to six host messages (`ready`, `response`, `stream`, `body-class`, `inline-style`, `link-element`) and dispatches only `ready` and the events the plugin's own UI server pushes with `pushEvent`; `savePluginConfig` is a request the page could make, never a notification it receives; and the server side (`HomebridgePluginUiServer`) has no save hook either. The Homebridge UI handles Save itself, writes config.json and shows its own restart prompt, so the shell's saved box is omitted here and the host's flow stands.

## 12. Security

1. Credentials are stored in config.json like every Homebridge plugin. The README states that Homebridge UI backups contain config.json and should be treated as containing secrets.
2. Optional `credentialsFile` on any provider: a path relative to the Homebridge storage directory (an absolute path is used as given) pointing to a JSON file whose keys override the provider's secret fields: `accountSid`, `apiKeySid` and `apiKeySecret` for Twilio; `username` and `password` for SMTP; `botToken` for Telegram; `token`, `username` and `password` for ntfy. It is read once during startup validation and again when the settings UI runs Test connection or Test send. A missing, unreadable, non-JSON, non-object, empty, or non-string-valued file is a blocking error at `providers[i].credentialsFile`; keys that are not secret fields of that provider type warn and are ignored (the key name is quoted escaped and cut to 64 characters); a notice logs which keys were taken from the file, never the values, and no message ever carries the file's text. Keeps secrets out of config.json, backups, and screenshots. Inline remains the default.
3. Twilio accepts API keys only. SMTP help steers users to app passwords. Telegram tokens are bot-scoped by nature. ntfy help recommends an access token over the account password; the token and password are redacted from every error and never logged.
4. No credential, message body (at info level), or raw provider error object is ever logged.
5. Custom UI server endpoints use submitted credentials in memory only, never persist or echo them, and only connect to the host the user configured. Every endpoint checks the shape of its payload, refuses a key named `__proto__`, `constructor` or `prototype` at any level, bounds the Test send switch id to 64 characters, and answers a plain result object; none throws.
6. TLS verification cannot be disabled.
7. Email subject and from name have CR and LF stripped. Telegram defaults to plain text.
8. Cooldown and master switch limit abuse from runaway automations.
9. Dependencies: nodemailer at runtime, plus `@homebridge/plugin-ui-utils`, which is listed as a dependency because the Homebridge UI loads `homebridge-ui/server.js` from the installed package (the plugin's main module never imports it and it has no dependencies of its own); libphonenumber-js and qrcode-generator in the UI bundle; everything else dev-only (esbuild for the bundle; bootstrap and playwright-core for the browser tests, which download nothing). `package-lock.json` is committed. Dependabot is enabled, without TypeScript major updates.
10. Publishing uses GitHub Actions with npm trusted publishing (GitHub OIDC) and provenance; no npm token is stored. Branch protection on `latest` requires a pull request.
11. "Download backup without credentials" (section 11.2, item 12) produces the file to share when asking for help: every secret field is an empty string and nothing else is removed. The README's Getting help section asks for it together with the relevant log lines. The unsaved draft in `localStorage` (section 11.2, item 23) is the same block without its marker: it never holds a credential, is written only after the user changes something, and has its secret fields emptied again when read; a restored draft takes its credentials from the saved configuration.
12. Size and time bounds (from the 1.1.0 review). Outbound: 10 s timeout per attempt, at most one retry after 2 s (or the provider's retry-after, capped at 60 s), at most 5 requests in flight per provider, response bodies read up to 1 MiB; SMTP uses 10 s connection, greeting and socket timeouts. Configuration: at most 100 recipients per action after deduplication, 200 entries per address list (a group's four lists, an action's extra recipients, a provider's sms senders), 20 actions per switch, 100 providers, 100 groups and 100 switches, 8 tags per action; each is a startup error naming the field and the limit, mirrored by the custom UI. Settings UI: Find people and groups makes one `getUpdates` call for at most 100 updates and lists at most 100 distinct chats with titles cut to 64 characters; Look up numbers reads one page of 20 numbers and 20 services; a backup file over 1 MB is refused before it is read and a draft over 1 MB is neither written nor loaded; Test send accepts a switch id of at most 64 characters. Keys named `__proto__`, `constructor` or `prototype` are refused at every nesting level by startup validation, every UI server endpoint, Restore from backup and draft recovery. Every log line has its control characters escaped and every quoted configuration value is escaped and cut to 80 characters (section 8, item 6); `EMAIL_PATTERN` rejects control and format characters; the ntfy title has control characters removed before it becomes a header. Dependencies: the runtime tree has no install scripts; the dev tree carries esbuild's postinstall and the optional macOS `fsevents`, neither published.

## 13. Packaging and release

1. Based on homebridge/homebridge-plugin-template. TypeScript, ESM, ESLint.
2. `engines.node`: `^22.12.0 || ^24.0.0`. `engines.homebridge`: `^1.6.0 || ^2.0.0`.
3. `keywords` include `homebridge-plugin`, `supports-hap` and `ntfy` (from 1.1.2). `supports-hap` is required: the Homebridge verification checker requires a plugin to declare the transports it supports (homebridge/plugins README, "Declaring Supported Transports"), and this plugin publishes HAP accessories only, so `supports-matter` is not declared. `ntfy` names the fourth channel for npm search, as `sms`, `twilio`, `email`, `smtp` and `telegram` do for the others. `displayName` is "Notify Switch".
4. CI workflow: lint, build and the harness (`npm test`) on Node 22 and 24 on every pull request and push to `latest`. The browser tests need Chromium: they fail on CI without one and are skipped locally. From 1.3.0 the workflow declares `permissions: contents: read` at the top level, and both workflows pin every action to its full commit SHA with the version tag in a trailing comment (`actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`, `actions/setup-node@820762786026740c76f36085b0efc47a31fe5020 # v7.0.0`, the commits the `v7` tags pointed at on September 12, 2026); Dependabot's github-actions updates keep the pins current. The harness never builds page code out of data: a fixture a stubbed server answer needs reaches the page as an init-script argument (`window.__fixture`, like the configuration as `window.__hbConfig`), and a link's host is checked by comparing `new URL(href).hostname`, not by searching the string. From 1.3.2 the browser tests render the host's own root sizing rule (`html, body { height: 100% }`) with the host's theme rules, so the page has to override it as it must in the real UI, and one unit test bundles the page's validator, copy and model reader from source with esbuild (a dev dependency the UI build already uses) to check the required-field messages against the label table (section 11.3).
5. Release workflow: triggered by publishing a GitHub release. It checks out, installs, lints, builds and tests on Node 22, upgrades npm to 11.5.1 or newer (which trusted publishing requires) and fails early if it is still older, then runs `npm publish --provenance --access public` with `--tag beta` when the release is marked as a pre-release and `--tag latest` otherwise. Authentication is npm trusted publishing through GitHub's OIDC token (`id-token: write`); no token secret is referenced. `--access public` is needed for provenance on a package's first publish and is harmless afterwards.
6. CHANGELOG.md maintained per version. GitHub release notes mirror it.
7. README structure: what it does, install, five-minute Twilio SMS setup, provider setup guides with links, groups, switches, HomeKit usage, template variables, cooldown and master switch, failure sensor, `credentialsFile`, backup, restore and reset, child bridge recommendation, security notes, troubleshooting, getting help, development, changelog link, about.

## 15. Open questions

Open for a later release:

1. Telegram `markdown` maps to the legacy `Markdown` parse mode (section 5.2). Should a `markdownv2` value be added for people who write bodies in MarkdownV2, or should `markdown` switch to it and the escaping burden move to the user?
2. Microsoft is retiring password sign-in for third-party apps on personal Outlook.com accounts (README, SMTP section). Should the Outlook.com preset stay, with its warning, or be removed once Microsoft completes the change?
3. Twilio email tracking. 1.1.1 set out to disable Twilio's open and click tracking on every send (open tracking inserts a tracking pixel, which got a message scored 5.7 as spam at Fastmail), but as of September 2026 there is no setting to turn it off, per message or per account: the Emails API documents no tracking field and the Email settings in the Twilio Console cover only event forwarding, IP addresses, and the address allow list, so nothing is sent (section 6.2). Should the endpoint gain one, the plan stands: disabled on every send, with an Advanced toggle on the Twilio provider card to re-enable it. That adds a configuration field and a UI string, so it belongs in a minor release, not a patch.
